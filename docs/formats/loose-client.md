# Loose data folders (a client without `data.sah`)

Some clients keep their data as plain files in folders instead of in `data.sah` and `data.saf`: an extracted client, or the `data` folder of a Shaiya-GX install. Shaiya Toolkit 0.5.0 reads such a folder as a client and can change it: add, replace and remove files, apply a patch, undo, and a health check, all through a journal kept in a backup folder you confirmed (the sections below). The folder is never converted, and nothing but the files you ask to change is written in it.

## Which folder is it

A folder you choose is looked at in this order. A folder that holds `data.sah` (in any letter case) is an archive client and is never a loose one.

| # | The chosen folder | `data` folder | install root |
|---|---|---|---|
| 1 | is named `data` and holds at least two of `Character`, `Item`, `Monster`, `World`, `Effect` (any letter case) | the chosen folder | its parent |
| 2 | has a `data` folder inside that holds two of them | `data` inside it | the chosen folder |
| 3 | itself holds two of them (an extracted client) | the chosen folder | the chosen folder |
| - | none of these | not a loose client: the Add dialog says which folders were looked for | |

Tests: `detect_finds_the_three_layouts_and_the_gx_flag`, `a_folder_with_data_sah_is_not_loose`.

**Shaiya-GX layout.** The folder is called a Shaiya-GX layout (converted media) when it holds a `*.ogg` under `Sound/` or a `*_dds.png` file anywhere in the first four levels (a bounded look at no more than 20,000 entries; running out of entries means "no"). Evidence: read from Shaiya-GX (their data-format document: Ogg Vorbis audio, PNG interface images, `_dds.png` for an atlas that was DDS). The toolkit shows these files as they are: a PNG is previewed as a picture, an OGG shows its header line, nothing is converted. Test: `detect_finds_the_three_layouts_and_the_gx_flag`; on a folder made from US EP4.5 files the opt-in test `an_extracted_copy_of_us_client_files_reads_as_a_loose_client`. "Works with Shaiya-GX" is not claimed: no Shaiya-GX folder was opened.

## What is listed

The toolkit lists the files once when the client opens and reads each through its listed path. Names are looked up without regard to letter case (`/` or `\`), and a name is taken as it is on disk (`%XX` is not decoded).

| Left out of the list | Why | The toolkit says so |
|---|---|---|
| a symbolic link or junction inside the folder | it could lead out of the folder | yes; test `a_symlink_inside_the_tree_is_refused` |
| names that differ only in letter case (all spellings) | which one the game would use depends on the system | yes; test `case_only_duplicates_are_reported_and_left_out` |
| `*.shaiya-tmp` files, and the top-level `shaiya-toolkit-backups` folder | the toolkit's own files | the temporary files are counted; test `the_backup_folder_and_temps_are_not_listed` |
| names that are not text or hold `:` or `\`, paths over 1,024 bytes, folders deeper than 16 levels | they cannot be looked up safely | yes, counted; test `caps_refuse_or_leave_out_and_say_so` |

More than 1,000,000 files refuse the folder (test `caps_refuse_or_leave_out_and_say_so`). A file over 4 GiB is listed with its size and is never read. A folder that becomes a link after it was listed is not followed: the read is refused (test `a_link_that_appears_after_the_listing_refuses_the_read`). A cancel ends the listing and a read (test `a_cancelled_listing_and_read_end_cancelled`). The folder you choose may itself be a link; only links inside it are refused.

A file's stamp (what a cache compares to know a file is the one it learned about) is its modification time and its length, read from the disk each time, so a file changed on disk is learned again (tests `a_file_changed_on_disk_changes_its_stamp`, `a_loose_file_source_reads_and_its_stamp_follows_the_file`). A change that keeps both the time and the length is not seen.

## The backup folder

Every write to a loose client needs a backup folder that the person confirmed: never inside the `data` folder and never a folder that was not chosen. The Add dialog shows a proposal and the person confirms or changes it; it is saved as `backups`. For layouts 1 and 2 the proposal is `shaiya-toolkit-backups` in the install root (outside `data`); for layout 3 there is no proposal. Until a backup folder is saved, the client is read-only ("choose a backup folder outside the data folder"). A folder inside `data` or equal to it is refused (also when it is a junction or link that leads into `data`, tests `a_backup_folder_inside_data_is_refused`, `a_backup_folder_that_is_a_junction_into_the_data_folder_is_refused`). Tests: `the_proposed_backup_folder_follows_the_layout_rule`, `a_backup_folder_inside_data_is_refused`, `a_layout_3_client_is_read_only_until_a_backup_folder_is_chosen`.

## Changing a loose folder

A change is a set of files to put (added when missing, replaced when there) and files to remove. Everything is checked before any byte is written, and one name that is not allowed refuses the whole change with the list (tests `a_name_outside_the_data_folder_refuses_the_whole_change`, `a_file_that_fails_its_reader_is_refused_before_anything_is_written`):

| Refused | Test |
|---|---|
| a name that leaves the data folder (`..`, an absolute path, a drive letter, an empty part), a name Windows would change (a trailing dot or space, `CON`, `NUL`, `COM1`, a forbidden character), `data.sah`, `*.shaiya-tmp`, the toolkit's backup folder name, a name over 255 bytes, a path over 1,024 bytes, a folder deeper than 16 levels | `a_name_outside_the_data_folder_refuses_the_whole_change` |
| a link or junction on the way, or a data folder that is itself a link | `a_junction_or_symlink_in_the_way_refuses_the_change_and_nothing_leaves_the_folder`, `a_data_folder_that_is_a_link_is_refused` |
| the same file listed twice, a put and a remove of one file, a file where another path of the change needs a folder, two new folders that differ only in letter case | `replacing_the_same_file_twice_in_one_change_is_refused`, `an_existing_file_keeps_its_spelling` |
| a remove of a file that is not there; an add of a file that is (command line) | `a_removed_file_moves_to_the_journal_and_comes_back`, `loose_replace_then_rollback_restores_the_bytes` |
| a known model, SData or texture file that does not read to its last byte (the same readers as the JSON export; an SEED file with a bad checksum or two wrappers) | `a_file_that_fails_its_reader_is_refused_before_anything_is_written`, `the_format_check_callback_refuses_a_bad_file` |
| more than 20,000 files in a change, one file over 512 MiB, all files together over 1 GiB (checked before the bytes are read) | `the_caps_hold_before_anything_is_allocated` |
| on a Shaiya-GX layout: any put or remove under `interface/`, `Sound/` or `Cursor/`, a `.wav`, `.ogg` or `*_dds.png` name, a `.dds` whose converted `_dds.png` sits beside it ("Shaiya-GX stores this as PNG/OGG: not changed"); the plain layout takes the same names | `converted_media_is_refused_on_a_gx_layout_and_allowed_on_a_plain_one`, `a_patch_with_interface_entries_is_refused_on_a_gx_layout` |

An existing file keeps its own spelling when the change names it in another letter case (test `an_existing_file_keeps_its_spelling`). Letter case is compared with Unicode lower case, as the listing does; two spellings of one name on a case-sensitive disk refuse the change (test `case_only_duplicates_on_disk_refuse_the_change`, Unix).

**What is written, in order.** The game must not be running: on Windows the toolkit opens `Shaiya GX.exe` or `game.exe` in the install folder exclusively and refuses while another program has it open (test `a_busy_game_exe_refuses_the_change`); when it cannot tell (no such file, or another system) it refuses until the person says the game is stopped (a confirmation in the Toolkit, `--yes-game-stopped` on the command line; test `an_unknown_busy_state_needs_the_confirmation`). Then the files must still be as they were when the change was planned (length and time of every target; test `a_change_made_between_plan_and_apply_is_detected`). Then, in the backup folder only: a journal folder `<UTC stamp>-<NNNN>-<label>/` (NNNN counts the changes of one second, so the names sort in the order they were made; test `changes_made_in_one_second_keep_their_order_whatever_their_labels`) with a copy of every file the change replaces or removes (`files/<path>`, each with its SHA-256) and `journal.txt`, and the marker `loose.toolkit-pending` (created only when there is none: two changes cannot run at once). Then each put is written to a temporary `.NAME.PID.shaiya-tmp` beside its target, read back, checked by the readers and renamed over the target (`write_atomic_checked`); each folder it needs is made one at a time and looked at for a link again; each remove is checked against the copy and deleted. Last the journal says `applied` and the marker goes. Nothing is written in any folder other than the data folder and the backup folder (tests `the_journal_goes_only_to_the_confirmed_backup_folder`, `the_journal_is_never_inside_the_data_folder`). A failure or a cancel puts every file back before the call returns and leaves the journal marked as not made (tests `a_failed_apply_leaves_the_folder_as_before`, `a_cancelled_apply_leaves_the_folder_as_before`); temporary files are removed (test `a_temp_file_never_stays_and_the_listing_never_sees_one`).

**Undo.** Only the newest applied change can be rolled back, and only while every file is as the change left it: a replaced file must still hold the new bytes, a created file must be there unchanged, a removed file must still be gone (tests `only_the_newest_change_rolls_back`, `rollback_is_blocked_when_a_file_changed_since`). An undo is a file copy back from the journal: replaced files come back, created files (and the folders the change made, when empty) are deleted, removed files return. The journal's copies are checked against their SHA-256 first, and a damaged copy blocks the undo before any file is touched (test `a_damaged_journal_or_copy_is_an_error_not_a_panic_and_blocks_the_rollback`). With `--force` (command line) a file that was changed since is first copied into the journal folder under `saved/` and listed, then the original is put back (test `rollback_is_blocked_when_a_file_changed_since`). The archive `rollback` refuses a loose journal and the loose history never lists an archive journal (test `archive_rollback_refuses_a_loose_journal`).

**Interrupted changes.** A crash leaves the marker and a journal marked `pending`. The next change, `shaiya loose recover` and the Toolkit's Health window undo the unfinished change from its journal (a file that is neither what the change wrote nor the original is saved under `saved/` first); an unfinished rollback is finished. Tests: `an_interrupted_change_is_recovered_on_the_next_open`, `the_next_change_recovers_an_interrupted_one_first`, `an_interrupted_rollback_is_finished`, `the_health_window_reports_a_loose_folder_and_recovers_an_interrupted_change`. Shaiya-GX documents that its client reads the data folder at start, so restart the game to see a change or an undo.

**What was not tried.** No real Shaiya-GX folder was changed and no change was run in a game: everything above is validated offline on synthetic folders.

## Health of a loose folder

`shaiya loose health CLIENT` and the Toolkit's Health window (Manage client folders > Health...) read the folder and write nothing. They report: files that are listed but cannot be read now; model and SData files that fail their reader (with the reader's reason); model textures that a list file (`.MLT`, `.MON`, `.ITM`) names and that are found nowhere in the folder, neither under the name nor as `.dds`, `.tga`, `.png` or `_dds.png`; list files that did not read; leftover `*.shaiya-tmp` files; the number of journals and how many can be rolled back; and an unfinished change, with a Recover button. The archive rules (dead space, shadowed files, index check) do not apply to a folder and are not run. Tests: `the_health_window_reports_a_loose_folder_and_recovers_an_interrupted_change`, `loose_replace_then_rollback_restores_the_bytes`. Texture resolution works the same on a loose folder as in an archive (tests `a_textured_preview_resolves_its_texture_on_a_loose_folder_as_in_an_archive`, `a_loose_folder_without_the_texture_file_draws_grey_and_says_so`, `a_loose_client_previews_a_model_with_its_list_texture_in_the_app`).

## Where it is used

| Program | What works on a loose client |
|---|---|
| Shaiya Toolkit | Add (with the detected layout and the backup folder), the picker and Manage dialog (`loose`, `Shaiya-GX layout`), the Archive tab: browse, search, filters, preview of every kind, Extract (copy out), Export as JSON, glTF, OBJ and BVH, Export folder as JSON; with a confirmed backup folder also Add, Replace, Remove and Apply (the queue, the four-row confirmation, one journal per Apply), the Apply & history tab (patches, history, Roll back, Prune), the Health window, and the SData tab on the client's files. Off: Compact, Save as new archive, Check, Use another archive pair (hover: "a loose folder has no archive"); Add, Replace, Remove and Apply without a backup folder ("choose a backup folder outside the data folder"). Tests: `a_loose_client_browses_and_previews_like_an_archive`, `archive_only_actions_are_off_for_a_loose_client_with_the_reason`, `a_loose_client_is_read_only_until_a_backup_folder_is_confirmed_then_queues`, `apply_on_a_loose_client_writes_through_the_loose_journal`, `a_failed_loose_apply_changes_nothing_and_keeps_the_queue`, `a_patch_applies_to_a_loose_client_from_the_apply_tab_and_rolls_back`, `the_sdata_tab_reads_the_files_of_a_loose_client` |
| `shaiya` | `clients add`, `clients list`, `clients show`, `info FOLDER` and `info @name`, `anim ... --from @name` (also a folder), and `shaiya loose list`, `add`, `replace`, `remove`, `apply`, `history`, `rollback` (alias `undo`), `prune`, `health`, `recover`. The archive commands (`archive`, `patch`, `clients health` and `clean`, `sdata --from`) refuse a loose client with exit 2 and say to use `shaiya loose`; the `shaiya loose` commands refuse an archive client with exit 2. Tests: `from_a_loose_client_reads_the_file`, `archive_commands_refuse_a_loose_client_exit_2`, `loose_commands_refuse_an_archive_client`, `loose_replace_then_rollback_restores_the_bytes` |

An entry that an older Shaiya Toolkit saved for a loose folder is listed there as an archive client, and that version drops `kind`, `data` and `backups` when it next changes the list ([toolkit-files.md](toolkit-files.md)). Version 0.5.0 offers "Detect as loose folder" in Manage client folders for an entry that has no `kind`, no `data.sah` and a folder that passes the detection (test `an_entry_without_kind_that_detects_as_loose_is_offered_for_redetection`).
