# Taking models and animations to other programs (glTF, OBJ and BVH)

For people who want to look at a Shaiya model or animation in a program that opens glTF 2.0 files (Blender and other viewers), or to start work from a game model there. The toolkit writes glTF, and reads a glTF back into a new game file (section 5); it also writes static meshes as Wavefront OBJ and reads them back (section 6), and writes an animation as BVH and reads back the layout it writes (section 7). Everything below is **validated offline** on test files and on the files of one client; the game was not involved.

**glTF, OBJ and BVH are a lossy view of the game file: the game file's own round trip (JSON) stays byte for byte; an import builds a new file and runs the same checks as `shaiya anim import` before it writes.** Use [the JSON export](replacing-an-animation.md) when you need the file's exact values; use glTF when you want to look at it elsewhere.

## 1. What goes out

| Game file | glTF holds |
|---|---|
| `.3DC` skinned mesh | the mesh, its skin (the bones and the file's own matrices), its material; with `--anim` one animation per `.ANI` you name |
| `.3DC` cloak (no bones) | a static mesh without a skin; an animation cannot be attached |
| `.ANI` animation | the skeleton at its reference pose and the animation: no mesh |
| `.3DO`, `.3DE` | the mesh at rest (the vertex frames are not written; a note says how many) |

A `.gltf` file comes with a `.bin` beside it that holds the numbers; a `.glb` is one file that holds both. Nothing is written into a client folder, and nothing that exists is replaced without `--force` (the same rules as the JSON export).

## 2. What the mapping does, in words

- **Axes.** The game's space is left-handed; glTF's is right-handed. The toolkit mirrors the front-to-back axis once (`z` becomes `-z`) in positions, normals, rotations and bone matrices, and swaps two corners of every triangle so the outside stays outside. Nothing else is mirrored.
- **Time.** Keys are 1/30 second. The first time in the file is the smaller of the animation's first field and its smallest key (some files start at -1 or -4, and glTF has no negative times); the file records it, and the animation's end key too. glTF files carry no frame rate: if a program asks, set its scene to 30 frames per second (a hint, not checked here).
- **Bones.** One node per bone in file order, named `Bone_000`, `Bone_001`, ... (the game's bones have no names; the number is the link back). A skin needs one common root: when the bones have none (a mesh without an animation, or a skeleton with several roots) the toolkit adds a node `Shaiya_Root` after the bones.
- **Skin.** The game gives each vertex two bones and one weight; glTF gets two joints and two weights. A vertex whose two bones are the same bone, or whose weight is exactly 0 or 1, lists one joint. The 16-bit `pad` field of each vertex goes into a custom attribute `_SHAIYA_PAD` so nothing of the vertex is lost.
- **Rest pose.** For a mesh the bones rest where the mesh's own matrices put them, so the mesh rests undeformed; the animation then carries the complete motion of every bone. A bone that no vertex uses may keep an identity rest when its matrix is not a plain placement.
- **Quaternions** are made continuous (the toolkit's pose model blends the short way round, which is its model of the game's blend: inferred, not checked in the game; other programs blend component by component and would spin the long way otherwise).
- **Textures are names only.** A material is named with the texture name of the file and keeps the raw bytes as hex in `extras`; no picture is written or embedded, and there is no `images` list unless you give `--texture-uri-base DIR`, which writes only `DIR/<name>.png` as a reference (a file that does not exist there makes viewers complain; convert the game's pictures yourself).
- **Names and paths.** A file holds the archive path or the file name of its input and the toolkit's version, never a folder of your machine.

## 3. What cannot go out

The toolkit refuses a file rather than writing something that plays differently, and names the bone or vertex:

- a vertex, normal, texture coordinate or matrix with NaN or an infinity (the reason says `vertex 287 holds NaN or an infinity in its normal x`),
- a bone whose placement is sheared (its rows not at right angles) or mirrored (negative determinant),
- keys that do not increase,
- a weight outside 0 to 1, or a vertex that names a bone the skeleton does not have,
- animations that do not share one skeleton, or an animation attached to a cloak,
- a mesh without vertices or faces, or a face that names a vertex that does not exist.

`--allow-lossy` projects a sheared, mirrored or NaN placement onto the nearest placement, and drops the keys that do not increase; the output says how many items it changed. A file with a projection is not posed against the source, and the output says so ("the pose check was skipped for this file"; `--json` has `pose_checked`). A bone no vertex uses, whose finite matrix is sheared or mirrored, is not a refusal; a matrix with NaN or an infinity is, whether or not a vertex uses the bone.

On US EP4.5 the opt-in test `every_us_client_ani_and_3dc_exports_or_is_refused_by_kind` writes 5,864 of the 5,940 `.ANI` and `.3DC` files and refuses the other 76, each with a reason by kind (of the 18 `.3DC` files refused for a value that is not finite, 6 hold such a vertex and 12 such a bone matrix; see [the format pages](../formats/README.md) for the files themselves).

## 4. How to do it

```
shaiya anim export "Character/Human/3DC/huwm_torso001.3DC" --from "@us" --format glb --anim "Character/Human/ANI/huwm_000_normal.ANI" -o torso.glb
shaiya anim export "Character/Human/ANI/huwm_000_normal.ANI" --from "@us" --format gltf -o walk.gltf
shaiya anim export "Monster/ANI/" --from "@us" --format gltf --out-dir gltf-out
```

`--format gltf` writes `walk.gltf` and `walk.bin`; `--format glb` writes one file. Exit 0 written, 2 a bad argument (an output name that does not fit the format), 3 the file cannot be written as glTF (the reason is printed), 4 the output exists, is inside a client folder or is the input, 5 a bug. With `--out-dir` every file is written as `<archive path>.gltf` and `.bin` (or `.glb`) under the folder.

In Shaiya Toolkit's Archive tab, right-click an `.ANI`, `.3DC`, `.3DO` or `.3DE` file and choose **Export as glTF...** (also in the command palette). Pick a `.gltf` or `.glb` name outside every client folder. An `.ANI` goes out together with the one mesh the Mesh box shows when you have chosen one; with the default parts or the skeleton chosen it goes out alone. The file is written by a background task and checked first.

## 5. Bringing a glTF back in

`shaiya anim import IN.gltf -o OUT.ani` (or `IN.glb`, and `-o` ending in `.3dc`, `.3do` or `.3de`) and the Toolkit's **Import model/animation...** read a glTF 2.0 file and build a **new** game file. They never change an existing file, and a file made by another program is read by the same rules (bones named as below; no file from another program was tried). Everything here is **validated offline**: how the game plays an imported file was not tested.

```
shaiya anim import walk.glb -o walk.ani --like "Character/Human/ANI/huwm_000_normal.ANI" --from "@us"
shaiya anim import walk.gltf -o walk.ani --like old.ani --keys exact
shaiya anim import torso.glb -o torso.3dc --like "Character/Human/3DC/huwm_torso001.3DC" --from "@us" --reduce-influences
shaiya anim import crate.glb -o crate.3do
```

- **What is made, and the like file.** The extension of `-o` says which game file is made. An `.ANI` and a `.3DC` need `--like`, the file the new one will replace (for a `.3DC`, the `.ANI` of its rig will do): without it the command stops with exit 2. A `.3DO` or `.3DE` takes no like file (exit 2 if one is given). An `.ANI` takes its skeleton (bone count, parents, reference matrices) and its first field from the like file, never from the glTF, and is written only when it passes the same check as `shaiya anim import` of a JSON (same skeleton, same first field, no validation error); otherwise exit 1 and nothing is written. A `.3DC` takes its matrices from the glTF's skin; it is written only when its bone count is the like file's and no vertex names a bone the rig does not have.
- **Which node is which bone.** A node named `Bone_NNN` is bone NNN, with any number of digits (`Bone_5` and `Bone_005` are the same bone). A node with another name needs `--map FILE` (lines of `node name = bone index`; blank lines and lines starting with `#` are skipped). A bone of the like file without a node, a node named for a bone the like file does not have, two nodes for one bone, and a bone whose parent differs from the like file's are refused, with the list.
- **Animation.** The file must hold exactly one animation. It is sampled at every whole key (30 per second), from its first time to its last, by glTF's own rules for `LINEAR`, `STEP` and `CUBICSPLINE`; times that are not multiples of 1/30 second (Blender at 24 frames per second, for example) are sampled at the whole keys and the command says so. A bone gets a rotation or translation track only when it moves, or when its value differs from the like file's own; a bone that stays where the like file has it gets none, so an imported file can have fewer tracks than the file it came from. `--keys exact` instead keeps the file's own keys (each time must be a multiple of 1/30 second, to within a microsecond and the precision of a 32-bit time, and the channel must be `LINEAR`). `--reduce` drops the keys that the keys around them reproduce within 1e-5. The result is **the same pose, not the same bytes**: a quaternion may come back with its sign changed, and keys may differ.
- **Skin (`.3DC`).** A game vertex holds two bones and one weight. A vertex with more than two influences is refused (the reason names the first vertex and how many there are); `--reduce-influences` keeps the two largest, renormalises them and says how many vertices changed and the largest weight dropped. A vertex that has one bone takes the like file's second bone and weight only when the like file's vertex of the same number has the same position and texture coordinate to the bit (an edited file whose vertices moved gets the one bone twice), which is what lets a `.3DC` the toolkit exported come back **byte for byte** with that file as the like file. The texture name comes from the material's `extras` (`texture_hex`, as the toolkit writes it) or else the material's name; a picture in the glTF is never read.
- **Static meshes (`.3DO`, `.3DE`).** The file must hold one mesh and no skin. The mesh node's own placement is applied to its vertices (and says so); a placement that mirrors the mesh is refused. A `.3DO` needs normals: when the file has none, they are computed from the faces and the command says so. No frames are written.
- **What is refused (exit 3, with the reason naming the node, bone or vertex).** A scale on a bone that the game would drop (the game replaces a bone's 3 x 3 by a rotation; a scale equal to the like file's own is kept), morph targets and morph-weight animation, animation of a node that is not a bone, more than one animation, a node with two parents or a cycle of nodes, a node above the skeleton that is not a bone and has a rotation, scale or move (the reason names the node: apply it in the program that made the file), a skinned mesh whose node has a placement, more than two meshes or more than one primitive per mesh, a mode other than triangles, more than 65,535 vertices, more than 256 bones, NaN or infinity anywhere, weights that do not add up to 1, sparse accessors, normalized or quantized (non-float) attributes, a required extension (compression, quantization or any other), a buffer that is a URL or lies outside the folder of the `.gltf` (only a `data:` uri or a file next to it is read; a symbolic link that leads out of the folder is refused too), JSON text over 16 MiB, a sampler of more than 160,000 key times, an animation or mesh whose accessors hold more than 33 million values together, a texture name over 255 bytes, a like file that is a cloak, and a file that is truncated, malformed or asks for more than the file holds.
- **Where it stops, and what it writes.** The output rules are those of the JSON import: a new file (an existing one only with `--force`), never inside a client folder, never one of the inputs, written beside and read back before it is renamed. Exit 0 written, 1 an `.ANI` that does not pass (nothing written), 2 a bad argument, 3 a refused or unreadable file, 4 the output rules, 5 a bug.

In Shaiya Toolkit's Archive tab, right-click an `.ANI`, `.3DC`, `.3DO` or `.3DE` file and choose **Import model/animation...** (also in the command palette; it reads a glTF, an OBJ or a BVH, sections 6 and 7). The row you clicked is the like file (an `.ANI` or `.3DC`) or names the kind (a `.3DO` or `.3DE`). Choose the glTF file (and a map file if you need one), tick the options, press **Import**: a background task reads and checks it, and the window shows what it made, or every reason it refused. **Save as new file...** writes it to a new file outside every client folder (the name must end in the kind's extension, nothing that exists is replaced; the file is read back and checked again before it is renamed); put it into a client with Replace.

## 6. OBJ: static meshes

`shaiya anim export X.3DO --format obj -o x.obj` (a `.3DE`, or a `.3DC` at rest, works the same) and the Toolkit's **Export as OBJ...** write a Wavefront OBJ; `shaiya anim import IN.obj -o OUT.3do` (or `.3de`) and **Import model/animation...** read one back into a **new** file. An OBJ holds no bones and no animation, so a `.3DC` can go out (at rest) but cannot come in, and an `.ANI` does not take part. Everything here is **validated offline**: no other program opening these files was tried.

```
shaiya anim export "Item/3DO/arrow.3DO" --from "@us" --format obj -o arrow.obj
shaiya anim import crate.obj -o crate.3do
```

- **What goes out.** The mesh as it lies at rest. The vertex frames of a `.3DO` are not written, and a note says how many (test `an_obj_note_says_what_was_left_out`); a `.3DE` goes out without its frames, and a vertex flag other than -1 is not written (the same test). A `.3DC` goes out with its positions, normals and texture coordinates as stored; its bones and weights are left out, and a note says so (`a_3dc_goes_out_at_rest_and_is_not_imported`). A vertex that holds NaN or an infinity refuses the file and the reason names the vertex (`an_unwritable_mesh_is_refused_with_its_vertex`).
- **The mapping, in words.** The same one mirror as glTF (a vertex `x y z` is written `v x y -z`, a normal the same), a triangle swaps its last two corners so its outside stays outside, and the texture coordinate `v` is written `1 - v` (OBJ puts the origin of a picture at the bottom left, the game's files at the top left). There is one `vt` and one `vn` for every vertex, so a vertex keeps its number: the faces read `f a/a/a c/c/c b/b/b` (`obj_flips_v_and_winding_and_back`, `a_3do_round_trips_through_obj`). The numbers are written with all their digits, so a mesh the toolkit wrote comes back with the same positions and normals to the bit, and the same texture coordinates to the bit except that a `v` of -0 comes back as +0 and a `v` smaller than about 1e-9 may come back as its neighbouring number (`1 - v` is formed in double precision); for the test meshes the bytes are the same too.
- **Textures are names only.** A mesh that names a texture gets a `usemtl <name>` line and a `.mtl` beside the `.obj` that holds `newmtl` lines and nothing else (no picture is named, written or read), and a comment `# texture-hex <hex>` with the raw bytes of the stored name, so a name with a tail after its NUL comes back unchanged. A mesh with no texture name makes no `.mtl` (`a_3do_round_trips_through_obj`, the CLI test `an_ani_exports_as_bvh_and_the_meshes_as_obj`). An existing `.mtl` is not replaced without `--force` (the `.bin` rule of glTF: `the_export_outputs_follow_the_json_rules`).
- **What the import takes.** Triangles and quads (a quad is split on its shorter diagonal), corners of the forms `v`, `v/vt`, `v//vn` and `v/vt/vn`, indices counted from 1 or, when negative, from the end of the list so far (`quads_and_negative_indices_import`). Corners with the same position, texture coordinate and normal are one vertex. The vertices keep the order of the `v` lines of the file, not the order of the faces; a vertex that no face uses is dropped (`an_unused_vertex_is_dropped_and_the_vertex_numbers_follow_the_v_lines`). `o` and `g` lines are read as one mesh; `s`, `l`, `p`, curves and any other line are not read, and a note counts them (`lines_that_are_not_read_are_counted`).
- **Normals.** A `.3DO` needs them: when a corner has none, the normals of the whole mesh are computed from the faces (each corner's face normal, weighted by area) and the command says how many corners had none (`missing_normals_are_computed_and_said`). A `.3DE` holds no normals; the file's are left out.
- **Texture name.** The material of the faces (`usemtl`) is the texture name, written in the game's text encoding (cp949) with its NUL. A `# texture-hex` line is used when it names the same texture as `usemtl` (or when there is no `usemtl`); when it names another one, the visible name wins and a note says so (`the_texture_comes_from_the_name_or_the_hex_and_a_conflict_says_so`). A name over 255 bytes, one that cp949 cannot hold, and a file that names two textures are refused.
- **The `.mtl` is never opened.** An `mtllib` line is counted and ignored whatever it names (a folder, a path outside the folder, a file that does not exist): the importer is a function of the bytes of the `.obj` and the library file that implements it has no file access (`obj_import_never_opens_mtllib`, in the library and through the command).
- **What is refused (exit 3, the reason names the line).** A corner with no texture coordinate (a mesh without them cannot be textured), more than one material (the reason lists them: a game mesh has one texture name), a face of fewer than 3 or more than 4 corners, an index that is 0 or past the list, a number that is not a number or is NaN or an infinity, a line that continues on the next one (a trailing backslash), a file with no faces, text that is not UTF-8, a file over 64 MiB, and a mesh that needs more than 65,535 vertices (the game's index is 16 bit; 65,535 are written and 65,538 refused) (`missing_uv_or_two_materials_are_refused`, `more_than_65535_vertices_are_refused`, `malformed_obj_is_an_error_not_a_panic`, and through the command `a_refused_obj_is_exit_3_with_its_reason_and_nothing_is_written`). Every limit is checked before the memory it guards is used, and a bad file is an error, never a panic.
- **In the Toolkit.** Right-click a `.3DO`, `.3DE` or `.3DC` file and choose **Export as OBJ...**: pick an `.obj` name outside every client folder (a `.mtl` of names is written beside it when the mesh names a texture, and one that is already there is not replaced). **Import model/animation...** reads an OBJ for a `.3DO` or `.3DE` row, with the same refusals shown in its window, and **Save as new file...** writes a new file only, outside every client folder, read back before the rename. An OBJ on an `.ANI` or `.3DC` row, and the glTF-only options with an OBJ, are refused with a message. The status line and the window carry the sentence above (`exporting_as_bvh_and_obj_writes_the_files_and_says_the_lossy_sentence`, `the_obj_and_bvh_commands_are_offered_for_their_kinds_only`, `exporting_as_obj_or_bvh_into_the_client_folder_or_to_a_wrong_name_is_refused`, `importing_an_obj_makes_a_new_3do_or_3de_and_refuses_the_wrong_rows_and_settings`).
- **Where it stops, and what it writes.** `-o` must end in `.3do` or `.3de` (exit 2 for another extension, for `--like`, and for any glTF-only option); the output rules are those of the JSON import: a new file (an existing one only with `--force`), never inside a client folder, never one of the inputs, read back before it is renamed. Exit 0 written, 2 a bad argument, 3 a refused or unreadable file, 4 the output rules, 5 a bug (`a_refused_obj_is_exit_3_with_its_reason_and_nothing_is_written`, `an_obj_comes_back_as_the_same_3do_and_3de`).

On US EP4.5 the opt-in test `every_us_client_mesh_exports_obj_and_a_3do_or_3de_comes_back` read 3,169 of the 3,171 `.3DO`, `.3DE` and `.3DC` files (two `.3DE` files are in a layout the toolkit's reader refuses), wrote 3,163 and refused 6 `.3DC` files, each for a vertex that is not finite; the 738 `.3DO` and `.3DE` files came back with the same triangle corners (position, normal and texture coordinate to the bit, so none of them has a `v` of -0 or below 1e-9), 733 of them with the same bytes once the frames are left out. The test asserts that no written file is refused by the import and that every corner matches; the 738 and 733 are measured and printed, not asserted.

## 7. BVH: an animation-only reference

`shaiya anim export X.ANI --format bvh -o x.bvh` and the Toolkit's **Export as BVH...** write an `.ANI` as a BVH (Biovision hierarchy) file, the motion-capture text format that animation programs read; `shaiya anim import IN.bvh -o OUT.ani --like TARGET` and **Import model/animation...** read back a BVH **laid out as the toolkit writes it**. It is an animation-only reference: it holds no mesh and no bind pose, it is lossy for bones that translate, and the import reads only files laid out as the toolkit writes them. Everything here is **validated offline**: no other program opening these files was tried.

```
shaiya anim export "Character/Human/ANI/huwm_000_normal.ANI" --from "@us" --format bvh -o walk.bvh
shaiya anim export "Character/Human/ANI/huwm_000_normal.ANI" --from "@us" --format bvh --drop-translation --scale 100 -o walk-cm.bvh
shaiya anim import walk.bvh -o walk.ani --like "Character/Human/ANI/huwm_000_normal.ANI" --from "@us"
```

- **What goes out.** One joint per bone, named `Bone_NNN`, in the bone tree of the file; its `OFFSET` is the reference translation of the bone (its offset from its parent, the same mirror as glTF); the root has the channels `Xposition Yposition Zposition Zrotation Xrotation Yrotation` and every other joint `Zrotation Xrotation Yrotation` (a rotation about Z, then X, then Y: the usual motion-capture order). The root's position channels are its absolute position. One frame for every whole key from the start key (the smaller of the first field and the smallest key) to the end key, `Frame Time: 0.0333333` (30 keys per second), each bone sampled as the game poses it (`a_known_three_joint_pose_writes_the_expected_channels_zxy`, `frame_time_is_one_thirtieth`). A forward kinematics written for the test from these rules puts every joint and a point in its frame where the game's own pose does, at every key (`the_bvh_poses_like_the_games_pose`).
- **Angles.** Each rotation is turned into three angles, in degrees with six decimals, and each frame takes the triple (every angle shifted by whole turns, or the second solution of the same rotation) nearest to the frame before, so a turn across 180 degrees does not jump (`euler_unwrap_across_180`). Close to gimbal lock (the X angle near 90 degrees) the angles are not determined by the rotation; Y then follows the frame before, and the output counts those frames in a note. Poses within 0.0001 degrees of that lock are still reproduced to 1e-4 (`poses_close_to_gimbal_lock_are_still_reproduced`).
- **Two or more roots.** A skeleton with two or more roots gets a synthetic root `Shaiya_Root` at the origin with no rotation that holds them (the import drops it), so the real roots become ordinary joints (`two_roots_get_a_synthetic_root`).
- **A bone that moves relative to its parent has no BVH form** (a BVH holds a constant offset for every joint). A non-root bone whose translation track moves it is refused (exit 3, the reason names the bone and how far it moves); `--drop-translation` leaves that motion out instead and the output says how many bones and the largest distance. A track that stays on the offset is not a movement (`a_translating_non_root_bone_is_refused_unless_dropped`; the command: `the_export_outputs_follow_the_json_rules`). A scale in the reference matrix of a bone that has no rotation track cannot be held either: only its rotation is written, and a note counts those bones. A matrix that is not a placement (NaN, shear, a mirror) and a key that is not finite are refused with the bone, and an animation of more than 100,000 frames, or of more than 16 million numbers (frames times channels), is refused (`a_translating_non_root_bone_is_refused_unless_dropped`). `--scale F` multiplies the offsets and positions (100 for tools that expect centimetres; the import reads scale 1 only).
- **What the import reads.** `--like` is required (exit 2 without it: `bvh_import_without_like_exits_2`): the skeleton, reference matrices and first field come from the like file, as for glTF. A joint is a bone by its name `Bone_NNN` (any number of digits); a joint the like file lacks or names twice, a bone with no joint, and a joint with another parent than the like file's are refused, with the list (`bvh_joints_that_do_not_match_the_rig_are_refused`). The channels must be the ones above in that order: another order, or a position channel on a joint that is not the root, is refused (`another_channel_order_or_frame_time_is_refused`, `a_non_root_position_channel_is_refused`). `Frame Time` must be 1/30 within 1e-6 second. Every `OFFSET` must be the like file's reference translation (to 1e-4 plus a part in 100,000), which also refuses a file made with `--scale` other than 1. A `Shaiya_Root` that moves, or whose `OFFSET` is not 0 (a tool that shifted the whole rig), is refused (`bvh_joints_that_do_not_match_the_rig_are_refused`). Frame 0 is the like file's start key. A rotation track is left out only when the like file's bone is posed the same way without it: its reference rotation, or the full reference matrix when the bone has a scale and no rotation keys; a scaled bone that has rotation keys keeps its track, because the game replaces the matrix's scale by the key's unit rotation (`a_scaled_bone_with_constant_rotation_keys_keeps_its_rotation_track`). The root's position track is left out when it equals the like file's own placement at every frame within 1e-5, so an animation that never moves comes back with no keys; the other tracks have a key at every frame, and the quaternions are made continuous (`bvh_round_trips_to_ani_poses_within_1e_4`). At most 20,000 frames, 64 MiB and 70,000 joints are read, each checked before memory is used (the number of values is counted before they are kept), and a malformed file is an error, never a panic (`malformed_bvh_is_an_error_not_a_panic`).
- **In the Toolkit.** Right-click an `.ANI` and choose **Export as BVH...**: pick a `.bvh` name outside every client folder. **Import model/animation...** on an `.ANI` row reads a BVH with that row as the like file; an `.ANI` that does not pass the rig check is shown with the differences and cannot be saved, and a BVH on another kind of row, and the glTF-only options with a BVH, are refused with a message (`importing_a_bvh_makes_a_new_ani_that_passes_and_saves_it`, `importing_an_obj_makes_a_new_3do_or_3de_and_refuses_the_wrong_rows_and_settings`).
- **Where it stops, and what it writes.** The result is written only when it passes the same check as `shaiya anim import` of a JSON (same skeleton, same first field, no validation error); otherwise exit 1 and nothing is written (`a_bvh_import_that_does_not_pass_exits_1_and_writes_nothing`). The output rules are those of the JSON import (`bvh_import_outputs_follow_the_import_rules`). Exit 0 written, 1 does not pass, 2 a bad argument, 3 a refused or unreadable file, 4 the output rules, 5 a bug. The result is **the same pose, not the same bytes**: it has a key at every whole frame, and the first quaternion of a track may come back with its sign changed.

By default the export refuses most stock animations: on US EP4.5 the opt-in test `every_us_client_ani_exports_bvh_or_is_refused_by_kind_and_comes_back` wrote 229 of the 3,509 `.ANI` files and refused 3,280, 3,278 of them because a non-root bone has a translation track; with `--drop-translation` 3,245 of the refused ones are written (the other 35 hold a value that is not finite or a mirrored matrix). The test asserts that all 229 come back through the import, pass against their source, and differ from it by less than 1e-4 in any matrix element over the sampled keys (measured: 0.000004, printed by the test). It also reads back the 3,245 files written with `--drop-translation`: every one is read and passes against its source, and the root bone of a one-root rig keeps its pose within 1e-3 (the pose of the bones whose motion was dropped differs by design and is printed, not bounded). The export writes up to 100,000 frames and 16 million numbers, the import reads at most 20,000 frames and 64 MiB, so a very long export is not read back by the import.

## 8. What was checked

Checked: the Khronos glTF validator 2.0.0-dev.3.10, run offline, reports no errors on the toolkit's output for its synthetic test files and for one US EP4.5 rig; not checked: Blender or any other program opening the files.

Before it writes, the toolkit also checks every file it makes (structure, ranges, finite numbers, weights, quaternions) and poses the exported skin (or the rig of an `.ANI` alone) the way glTF defines it at ten times, comparing it with its own renderer; a failure is exit 5 and nothing is written. The pose is not compared when `--allow-lossy` projected something, and the output says so. A second mesh with its own matrices is posed exactly when an animation plays; at rest it is not expected at its source positions, because it has its own skin.

The import: a `.3DC` the toolkit exported comes back byte for byte (test `a_3dc_round_trips_through_gltf_to_the_same_bytes`), an `.ANI` comes back with the same poses (`an_ani_round_trips_with_keys_exact_to_the_same_poses`), and every refusal above has a test that names its reason (`each_refusal_names_its_reason`, `sampler_rules_step_cubic_and_24_fps_resampling`, `malformed_files_are_errors_not_panics`). On US EP4.5 the opt-in tests measured: the first animation of each of the 16 character rigs and their 96 default parts come back (each `.ANI` passes against its source with `--keys exact` and with every whole key, with the largest pose difference 1.1e-6; each of the 96 `.3DC` files byte for byte; the test fails if the export refuses any of them), and all 3,462 `.ANI` files that the export writes come back with `--keys exact` and pose alike within a relative 1.2e-5 (measured, printed by the test; the test allows 1e-4) (`us_client_gltf_round_trips`, `every_exportable_us_ani_imports_back_with_keys_exact`). Blender's own files were not tried.

OBJ and BVH have no outside validator: they are checked by the toolkit's own tests only (the mapping against hand-worked values, the BVH against a forward kinematics written for the test and the game's own pose, every refusal against its reason, and the files of one client in the opt-in tests of sections 6 and 7). Not checked: Blender or any other program opening these files, and an OBJ or BVH made by another program.

The tests that stand behind these sentences are in `crates/shaiya-clientdata/tests/gltf_export.rs`, `crates/shaiya-clientdata/tests/gltf_import.rs`, `crates/shaiya-clientdata/tests/gltf_optin.rs`, `crates/shaiya-clientdata/tests/obj_bvh.rs`, `crates/shaiya-clientdata/tests/obj_bvh_optin.rs`, `crates/shaiya-cli/tests/gltf.rs`, `crates/shaiya-cli/tests/obj_bvh.rs` and `crates/shaiya-toolkit/tests/toolkit.rs`.
